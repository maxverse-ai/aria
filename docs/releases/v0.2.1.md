# Aria Internal v0.2.1

Aria 0.2.1 completes the first production-capable Trigger Platform on the 0.2
stable line. It turns the read-only trigger contracts introduced in 0.2.0 into
a durable, recoverable, channel-neutral execution system while preserving the
Supervisor as the single runtime owner.

This internal snapshot is distributed through the private GitHub repository. It
is not published to npm.

## Added

- Added durable schedule definitions, occurrences, leases, outcomes, audit
  records, recovery, idempotency, and recurrence calculation.
- Added the Supervisor-owned trigger manager, which discovers due occurrences,
  claims them, creates validated `RunIntent` values, and dispatches work through
  the existing agent runtime rather than introducing a second executor.
- Added result routing for history-only runs and channel-neutral conversation
  delivery, with durable delivery checkpoints and retry behavior.
- Added management APIs and `aria trigger` CLI operations for planning,
  creating, inspecting, updating, pausing, resuming, snoozing, running, and
  cancelling schedules, plus history and audit inspection.
- Added conversation-reminder parsing and confirmation flows without coupling
  schedule storage or execution to Lark.
- Added scoped, expiring bearer grants so agents can manage reminders through
  the same API boundary without direct filesystem, database, or timer access.
- Added a synthetic push-provider reference implementation and end-to-end
  extension proof covering provider ingress, durable occurrence creation,
  restart-stable deduplication, execution, and lifecycle draining.

## Console and operations

- Added Astryx-based trigger views to the independent Supervisor console,
  including schedules, history, audit data, runtime state, and management
  actions.
- Added deployment diagnostics and runtime capability metadata for staged
  enablement through `ARIA_TRIGGER_RUNTIME=enabled`.
- Kept the Trigger Platform independent of any single channel: Lark and future
  sources remain adapters at ingress and delivery boundaries.

## Safety and recovery

- Schedule mutations are validated by the management layer and persisted before
  acknowledgement; the CLI is an adapter to that boundary rather than an
  alternate state owner.
- Exactly-once side effects are not claimed. The system provides durable
  at-least-once execution with idempotent occurrence materialization, leases,
  fencing, retry policy, and auditable terminal outcomes.
- External provider identity is treated as evidence, never authority. Provider,
  profile, instance, source kind, and scope bindings must match a durable active
  definition before ingress is accepted.
- Agent grants constrain profile, engine, principal, schedule kinds, frequency,
  lifetime, and operation scope. Grant secrets are displayed once and only a
  digest is persisted.

## Upgrade guidance

- Upgrade global installations from 0.1.6 or 0.2.0 through the normal
  `aria update` plan/apply flow after active conversations have drained.
- Enable scheduled execution explicitly with
  `ARIA_TRIGGER_RUNTIME=enabled`; definitions and history remain durable across
  Supervisor restarts.
- Keep existing channel profiles unchanged. Trigger sources and result sinks
  resolve through registered adapters and the existing profile/runtime model.
- Preserve the updater's previous active version as the automatic rollback
  target until Supervisor, console, trigger runtime, and channel health checks
  pass.

## Distribution guarantees

- The internal release is created only from the exact merged `main` commit.
- The tarball, artifact manifest, checksum file, release contract, and
  standalone installer are verified before the draft is published.
- Repository-level GitHub Release immutability prevents replacement of the tag
  or uploaded assets after publication.
- The updater performs a planned version switch with restart safety checks,
  health verification, and rollback support.
