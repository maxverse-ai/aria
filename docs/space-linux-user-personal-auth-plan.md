- 更新日期：2026-09-10。
- 状态：执行后端正在实现，尚未完成生产接入、迁移或上线。用户已追加授权完成验证后上线；首先只在 `***REMOVED***-deepseek` 验证并回群汇报，再处理其他 ***REMOVED*** 容器。
- 决策：Aria 为每个 Space 管理一个 Podman 执行容器，按需启动、空闲停止；同一 Space 同时最多一个活动容器实例。宿主环境与 Aria 自身的部署运行时不作要求。

## 1. 已知现状与设计依据

前次部署核查显示 ***REMOVED*** 为 Docker 内非 root 5011:5011、cap-drop ALL、no-new-privileges、只读根文件系统；Space 使用 trusted-process，Codex full 权限映射为 danger-full-access。Space Podman 驱动尚未验证；先前 Linux 沙箱入口曾报告 bwrap 无权创建 namespace，不能据此断言 Podman 必然失败，也不能假设换运行时就能成功。

前次盘点包含 13 个 Space、72 条封存旧会话，以及 prepared Space 启用之后新增的会话/产物；这些是历史观测，不是迁移时的最终数量。正式实施必须重盘点当前活动 preparation、实际版本、会话目录和新增写入。

已上线的旧 socket 地址修复解决调用可靠性：客户端解析当前入口，但不替换或续期旧任务票据。该修复继续保留，不把隔离改造当作它的替代品。文件生成、上传、发送回执分别验证。

代码落点应复用并扩展：`src/space/launch.ts`、`runtime-registry.ts`、`engine-runtime.ts`、`preparation-store.ts`、`session-migration.ts`、`grants.ts`、`tool-credentials.ts`、`src/lark-cli/space-credentials.ts` 及 Codex app-server 适配器。目前服务侧启动 lark-cli 的路径不会自动进入 agent 沙箱，必须明确保留为受保护授权入口。

## 2. 目标架构与可信边界

```text
Aria：消息接入、Space 管理、任务调度（部署方式不限）
├─ 受保护的 Podman 执行适配器
│  ├─ Space A → 容器 A（按需运行）
│  ├─ Space B → 容器 B（按需运行）
│  └─ 团队 Space T → 容器 T（成员任务共用此容器边界）
├─ 个人授权服务：独立 lark-cli 配置、OAuth 与刷新
└─ 持久数据、身份映射、迁移回执、审计
```

Aria 核心只依赖通用执行环境接口，Podman 是当前实现的适配器，不规定 Podman 在裸机、虚拟机、现有容器内部或其他受控节点运行，不要求 Docker→Podman 迁移或 Podman-in-Podman。部署提供连接、存储、网络和资源能力；本方案不选择宿主拓扑。

执行适配器提供 ensure/start/exec/status/stop/remove、健康检查、资源配置和受限产物传输，认证、重连与错误由适配器统一处理。本地与远端部署的路径语义须明确：远端 Podman 的挂载源属于执行节点，不能把 Aria 本地路径当成远端路径；通过存储标识解析或受控传输解决。agent 不可直接调用管理 API。

Aria 管理服务不直接执行模型生成的代码；Space 容器运行 agent 引擎、shell、文件工具及本地浏览器/MCP。外部服务型工具逐项校验主体和资源，不能成为代读文件或切换身份旁路。

可信边界包括执行节点内核、管理/授权服务和镜像供应链。容器是跨 Space 边界，团队 Space 的文件、历史及 bot 结果属于共享数据；个人 Space 的数据和授权不进入团队容器。容器共享内核，不宣称可防御宿主管理员或所有内核漏洞。

部署能力预检验证 Podman 版本、UID 映射、挂载、网络和资源限额；实际 rootless/rootful、seccomp/LSM、存储驱动由部署配置选择并通过验收。能力不足阻塞上线，不自动使用 privileged、取消限制或回退 trusted-process。历史 bwrap 失败只是当时环境观测，不是所有部署的前置结论。

## 3. Space、个人身份与生命周期

| 对象 | 归属/职责 | 生命周期 |
| --- | --- | --- |
| profile | 接入、公共配置、管理服务 | 长期 |
| 授权主体 principal | 应用、租户、真实用户 | 长期 |
| Space | 文件、会话、成员权限 | 长期 |
| 执行环境 | profile + Space（唯一容器登记键） | 按需启动、空闲停止 |
| task/ticket | 单次任务、原发言人准入、允许操作、返回目标 | 短期、可撤销 |
| 容器实例 generation | 当前启动实例、运行时连接 | 每次重建更新 |

每个 Space 恰有一个逻辑容器槽位；停止时可以保留停止的容器或仅保留登记与数据，启动时创建实例。镜像/策略版本是实例属性，不得变成同时启动第二个容器的理由。升级先排空并停止旧实例，再启动新 generation，不采用同 Space 双活切换。

团队 Space 的所有成员共用该 Space 的容器、原生运行时和群聊历史，业务身份固定为该应用的 bot。发言人仍用于准入、审计、任务范围和回复目标校验，但不会触发个人凭据查找或 runtime 切换。

个人 Space 固定使用所属用户的授权。两个人的个人 Space、共享 Space 分别有独立容器和持久数据，不能互相挂载。共享 Space 内不承诺成员间私人文件隔离，因为个人数据应留在个人 Space；无需成员 UID、成员私有 HOME、按成员拆分 app-server 或为身份切换新增队列。现有会话调度和资源限制继续生效。

真实主体来自可信消息事件，模型传入的用户名、open_id、容器名和 profile 参数不授予身份。凭据索引包含应用、租户、用户，跨应用标识须验证映射。子任务继承权限范围，不能通过新建容器或代理调用扩大权限。

Space 删除、容器停止、任务结束、撤销个人 OAuth 是四个不同动作。停止执行容器不删除个人数据或撤销长期授权；删除 Space 需单独的数据保留流程。

## 4. 按需启动、回收与故障恢复

状态建议：`stopped → starting → ready → busy → draining → stopped`，另有 `failed`。持久化期望状态与实际容器 ID、generation，服务重启时对账；不能只依据内存中的进程对象判断运行状态。

1. 请求入队并确认真实主体、Space 成员权限、任务范围和资源预算。
2. 对执行环境键加锁，幂等创建/恢复容器；并发请求不得启动重复实例。
3. 使用固定镜像 digest 和挂载清单，建立当次受限工具通道，健康检查后连接 app-server。
4. 验证线程与 Space 归属后恢复历史会话；共享 Space 保留共用 runtime，不能跨 Space 复用。
5. 同一 Space 中的不兼容操作串行；子任务计入同一资源预算，不能借并发绕过限额。
6. 活动任务、文件上传、持有租约的后台任务结束后才进入空闲计时；初始候选空闲时间 10 分钟，属于待压测参数。
7. 空闲到期先拒绝新分配、撤销当前任务票据、关闭运行时、优雅停止，再按超时终止；确认所有容器进程退出。
8. 保留持久数据，清理临时 socket、短期票据与可丢弃层。下次启动分配新 generation 和票据。

容器崩溃/OOM、Aria/执行服务重启、宿主重启必须对账并清理孤儿实例。工具业务写入使用可验证幂等键或结果回执，恢复不能盲目重放发送、上传、创建等操作。后台任务必须登记期限、资源与所有者，无登记进程不得无限阻止回收。

## 5. 文件、执行与管理权限

- agent 进程默认非 root；容器 UID 由可信管理侧选择，agent 无权切换，容器生命周期进程与任务进程权限分开；最小 capabilities、no-new-privileges、只读基础镜像；写入限定工作目录、私有状态和有容量上限的临时目录。
- 只挂载该 Space 的获准数据，团队目录按群组共享语义处理，管理文件、全体 Space 根目录、凭据根目录不得挂载。
- 镜像 digest、挂载源、网络和资源策略由管理服务决定，模型不能任意传入 Podman 参数、宿主路径或设备。
- agent 不得接触 Podman 管理 socket、存储 graphroot、任意 exec 管理接口或启动器的管理凭据。
- 管理服务接口只提供受限的启动/停止/状态操作，校验调用主体和执行环境；启动参数使用结构化 argv，禁止 shell 拼接。
- 清理传给执行环境的环境变量、文件描述符和管理密钥。由部署生成合法的 LARK_CHANNEL/profile 绑定，保留约定变量；不靠清空变量或改普通 profile 绕过校验。
- 个人文件、会话、浏览器登录态和缓存默认私有；共享工具/镜像只读。可写共享缓存存在污染风险，不把私有数据混入公共缓存。
- 网络不默认共享 host；禁止任意访问管理端口、其他执行容器和敏感元数据端点。模型/API 所需出站及授权入口明确放行，具体网络实现由兼容性验证确定。
- 授权服务的文件上传等操作不能接受任意管理侧路径；使用归属校验后的产物标识/受限文件传输，防止服务代读越权。
- UID/GID 映射需持久记录，防止卷所有权冲突；不得假设现有服务 UID 5011 与容器映射后的数字等价。

## 6. 个人 lark-cli 与其他应用授权

采用独立受保护授权服务，保存每个人独立的 CLI 配置和刷新状态；个人 token 不放在 Space 容器、团队目录或模型环境中。agent 使用受控调用入口，服务侧 CLI 才接触个人凭据。将授权服务视作高价值可信组件，其日志、备份、子进程和配置也需隔离。

调用链：真实事件 → Space/principal/task/generation 绑定 → 核验票据、动作与资源范围 → 按 Space 选择 bot 或所属用户 CLI 环境 → 执行 → 脱敏审计和结果回执。

票据应短期、限范围、可撤销，与容器实例、principal 及任务绑定；不得靠来源 IP 或仅 Unix UID 代替授权。禁止伪造主体、跨容器复用、跨任务续用；入口重建不续期旧票据。

多人共享 Space 的业务请求固定使用 bot，即使发言人已有个人授权，也不得读取、借用或切换到该授权；显式 `--as user` 拒绝。个人 Space 在启用个人授权的新部署中固定使用本人 user；授权缺失、失效或权限不足不回退 bot，显式 `--as bot` 拒绝。历史 bot-only 部署配置保留兼容，迁移时显式开启个人 Space 授权能力。OAuth 登录不修改此身份策略。

OAuth：群里仅提示私聊；私聊在正确个人绑定下发起无等待流程，把返回链接原样交给本人并结束该轮；本人回复后完成同一流程，核验授权主体与发起人一致。取消停止、过期重发、身份不匹配拒绝绑定。策略拒绝和 profile 绑定失败不能当作缺授权反复登录。

个人工具授权绑定不设置 Aria 内部固定有效期，不因 30 天期限、容器停止或服务重启要求重新登录。旧 v1 授权存储加载时原子迁为 v2，移除历史 grant 的 expiresAt；已删除/撤销记录不重建。飞书凭据验证、刷新/撤销、OAuth 待完成事务有效期和单次任务票据有效期继续独立执行。旧版程序不支持 v2 存储，回滚须使用明确的兼容迁移，不能直接用旧二进制读取新存储。

授权按应用/租户/个人串行刷新、原子落盘，处理撤销与崩溃恢复。日志不得记录 token、device_code、应用密钥。个人可读取某文档不等于允许把内容公开到团队群；返回会话和产物可见范围是任务范围的一部分。

Git、浏览器、其他 API 与 MCP 连接逐项登记身份策略。无法代理的连接器使用限定主体的专用执行配置并说明凭据暴露边界；不得偷偷继承全局 profile 的个人登录态。

## 7. 磁盘、内存、CPU 与容量策略

总内存 = 公共服务 + 活跃执行环境进程 + 网络/存储/运行时辅助进程；总磁盘 = 共享镜像 + 各主体数据/依赖/缓存 + 历史镜像/备份。停止容器应释放任务进程，Space 数量不等于常驻进程数量。

- 同一受保护存储库共享只读镜像层，使用固定 digest；不要求每个 Space 各开一套镜像存储。
- Podman graphroot 由部署管理，放在受保护、容量明确的持久存储；验证存储驱动兼容性，若只能 VFS，单独测空间与 I/O 并决定是否接受。不要求特定嵌套存储布局。
- 工作数据使用独立持久目录，可写层只放可重建内容；会话、产物、授权状态不能依赖容器可写层生存。
- cgroup 委派、CPU/内存/PID 限额必须实测，验证每个 Space 限制生效且总量符合执行节点预算。磁盘配额另外实现，不能把 cgroup 当作磁盘容量配额。
- 配置全局活跃容器上限、每主体并发限制、排队超时、空闲回收时间、数据/缓存/日志配额和保留期限。
- 容量准入给管理服务、授权服务、系统和 I/O 留余量；不以全部容器的标称上限都能同时使用为前提。
- 自动清理不再引用的镜像和缓存，不删除活跃实例、迁移快照及仍在回滚窗口的版本。

不承诺未经压测的开销百分比。基准比较相同应用版本与任务：当前进程模式、按需 Space 容器模式；测 0/1/2/预算允许的更多并发，覆盖 API 等待、依赖安装、小文件读写、压缩上传、纯计算。记录 cgroup 内存/峰值、CPU 时间、冷/热启动 p50/p95、I/O、网络、磁盘独占/共享空间、回收后残留进程。避免简单相加 RSS 重复计算共享页。P0 设定可接受的预算与延迟门槛，P1/P5 必须给出实测结论。

## 8. 历史数据迁移

迁移起点必须是当前活动 preparation 和所有后续写入，不能仅重新导入 72 条封存会话。现有 prepare/迁移入口是否支持已激活布局升级需先核查；增加有版本的升级流程，不通过回退到旧 preparation 绕过检查。

迁移清单记录源/目标、数据类型、profile/Space/principal、成员权限、数字所有权和 UID 映射、大小/校验值、线程关联、路径映射版本、状态与错误。未知归属进入受保护待核实区，不能按文件名猜测或分发给所有成员。

| 数据 | 迁移策略 |
| --- | --- |
| 个人项目、文件、产物 | 复制到所属持久目录，校验后仅挂载给对应执行环境 |
| 团队项目 | 保留群组共享目录、历史和 bot 业务产物；个人资料仍在个人 Space |
| 历史会话、线程、任务记录 | 保留稳定标识与关联，核验线程归属；无法安全续接则保留归档并明确新线程关联 |
| 历史绝对路径 | 优先在该容器内部保持兼容路径；否则使用受控映射，不全局字符串替换或跨主体软链接 |
| 新旧 preparation 元数据 | 版本化升级，保留来源、映射、校验和切换回执 |
| bot 凭据 | 保留在受保护服务，为共享 Space 提供 bot 调用，不能转换为个人 OAuth |
| 已有个人授权 | 核验应用/租户/用户和 CLI 存储兼容性后迁入授权服务；不能确认则重新授权 |
| 无个人授权的成员 | 各自私聊 OAuth，不复制他人的 token |
| socket、旧票据、PID、运行时地址 | 全部重新创建或失效，不当作可续接的授权 |
| 缓存与安装依赖 | 优先镜像化或重建，保留必要离线依赖清单 |
| 混合日志、备份 | 管理侧限权保留，过滤敏感内容，不挂载到执行容器 |

迁移工具需要 dry-run、版本检查、幂等重跑、断点恢复、源目标冲突检测和逐项校验。复制优先，切换前不删除源；不能覆盖目标的新写入。软链接、硬链接及路径逃逸单独验证，映射后的 chown 不得递归修改公共管理目录。

可提前预复制大文件，但最终一致性备份和增量同步在 profile 停写窗口内完成。优先提供逐 Space 排空、停写、切换执行驱动；若现有 preparation/存储升级只能 profile 级切换，则明确安排该级别停写窗口，不承诺零停机。宿主运行时迁移不在本方案范围。记录消息接入游标/去重状态，确保新旧实例不会同时消费并重复执行。

## 9. 分阶段实施计划

| 阶段 | 工作与交付物 | 退出条件 |
| --- | --- | --- |
| P0 盘点与可行性 | 当前部署、数据清单、全部工具入口、执行节点能力、存储/cgroup/网络方案、资源与延迟预算 | 明确 Podman 执行可行条件、主体归属和实施边界；不可行则停止上线 |
| P1 双环境原型 | 部署中立的两个测试 Space，各一个容器，并验证团队容器固定使用 bot；固定镜像、受限挂载、启动/停止/恢复、资源限制 | A/B 越权被拒绝；无管理 socket 泄露；限额有效；给出性能基线 |
| P2 执行层接入 | Aria 执行驱动、Space 唯一容器键、按 Space 的 runtime key、队列、锁、generation、健康检查、空闲回收、重启对账 | app-server/工具全路径受控；并发不重复启动；回收无残留 |
| P3 个人授权 | 授权服务、个人 CLI 环境、OAuth 核验、刷新/撤销、工具返回可见范围、共享 bot/个人 user 策略及个人 Space 禁止 bot fallback | 两个人及团队场景不串身份；缺授权明确失败 |
| P4 迁移与回滚工具 | 当前 preparation 升级、dry-run 清单、备份/校验、路径和 UID 映射、增量保护、切换回执 | 在历史副本上幂等迁移与回滚，不丢新增数据 |
| P5 综合演练 | 历史续聊、附件真实交付、冷/热启动压测、OOM/断网/Aria 与执行服务重启、授权撤销、配额触发 | 达到 P0 门槛，故障恢复不重复写入且不改变 Space 身份 |
| P6 执行驱动切换与灰度 | 按支持的停写粒度切换 Space 到 Podman 驱动，先验证两个个人 Space 和一个团队 Space | 健康、数据校验、个人/团队任务和发送回执通过 |
| P7 分批开放与收尾 | 更多主体开放、容量调整、观察期、旧凭据/镜像清理、运维手册 | 迁移清单闭环，无旧执行旁路，回滚演练和监控完备 |

每阶段留下版本、配置摘要、脱敏测试证据、失败项和迁移回执。P2/P3 接口设计可协调，但上线顺序不能跳过可行性与迁移验证。本计划不承诺未经盘点支持的工期。

Aria 仓库负责通用执行/身份/授权/迁移接口；***REMOVED***/***REMOVED*** 部署负责执行连接、镜像、持久卷、UID 映射、网络与 cgroup 委派、部署和回滚；宿主运行时不作为 Aria 功能要求。分别遵循仓库工作流，不手改 vendor/aria 或运行容器；生产切换遵循用户指定的 DeepSeek 优先范围和完整门禁。

## 10. 切换与回滚

切换：暂停接收/分配任务并保存去重状态 → 排空或按批准策略中止在途任务 → 一致性备份及最终增量 → 校验迁移目标 → 停止目标 Space 的旧执行进程 → 启动对应 Space Podman 容器 → 健康与业务验证 → 开放灰度。

保留旧执行版本、配置和不可变源快照，绝不让新旧实例同时写同一数据目录。候选 Podman 测试实例默认不接生产事件、不使用真实业务写权限。

回滚触发包括身份串用、数据校验失败、限额无效、持续无法启动或超出已定资源预算。新系统发生写入后先停写、保存并核对增量，执行已演练的反向兼容迁移或保留只读数据；不能直接指向旧快照丢弃新增记录。旧模式若无法维持已承诺授权边界，则保持业务暂停，不为恢复可用性让个人 Space 回退 bot 或让共享 Space 借用个人授权。

观察期结束后才按保留政策删除旧数据、旧镜像和凭据副本。销毁容器本身不会撤销外部 OAuth，撤销流程独立执行。

## 11. 验收矩阵

- 个人 Space A 无法读取/修改个人 Space B 的文件、线程、缓存、凭据；团队 Space 的资料按群组共享。
- 改 HOME/profile、直接 CLI、伪造用户/Space、越权路径、连接其他容器或重放票据不能获取他人权限。
- shell、文件工具、浏览器/MCP 和服务代执行路径均验证，没有只隔离 shell 的旁路。
- agent 无法访问 Podman API/graphroot、任意挂载、任意管理 exec、跨容器网络入口。
- 个人授权不足、失效、撤销均明确失败，无 bot fallback；双人刷新不串存储。
- 同一团队 Space 两位发起人在同一个容器中执行，均用 bot；个人授权记录对共享 Space 不可解析，容器实例数量始终为一。
- 并发启动只有一个有效实例；空闲回收、Aria/执行节点重启、崩溃和 OOM 后无有效旧票据或孤儿进程。
- 任务回执和幂等恢复防止重复创建、发送、上传；产物验证包含实际上传和消息发送结果。
- CPU/内存/PID/磁盘限制实测有效，单任务耗尽预算不拖垮接入和授权服务。
- 历史数量/校验、线程关联、路径访问、UID 映射、最新新增数据和回滚增量全部核对。
- Space 一对一容器映射、冷/热启动、峰值内存、I/O、空间增长、回收后资源达到预算；没有未经测量的“零开销”结论。
